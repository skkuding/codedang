# Local collaborator fixtures

Run from `apps/backend` with the local client API running:

```bash
node scripts/collaborator-test.cjs setup
```

`setup` creates/reuses six `collab_*` users (all global role User) and a dedicated Draft Problem A. It resets only participation on that marked problem; do not use it for real work. No migrations or database-wide reset run. The fixed local-only password is `CollabLocal123!`; optionally set `COLLAB_TEST_PASSWORD` for both commands.

| Account         | Problem A role / status |
| --------------- | ----------------------- |
| collab_owner    | Owner / Approved        |
| collab_editor   | Editor / Approved       |
| collab_reviewer | Reviewer / Approved     |
| collab_pending  | Editor / Pending        |
| collab_rejected | Reviewer / Rejected     |
| collab_outsider | No participation        |

Refresh tokens without resetting collaboration state:

```bash
node scripts/collaborator-test.cjs login
```

The script loads backend `.env`. It accepts only loopback PostgreSQL and HTTP URLs and refuses NODE_ENV=production. Ensure the local DB is disposable development data, not a port-forward to a shared server. `COLLAB_CLIENT_URL` defaults to http://127.0.0.1:4000; `COLLAB_GQL_URL` defaults to http://127.0.0.1:3000/graphql. Both APIs must use the same DB and compatible JWT configuration.

In **Codedang Admin**, open **Mandeuldang Collaborator**, select **Local**, and run the API requests. These requests include `X-Collaborator-Test: true`, which skips the collection admin auto-login and preserves their account-specific bearer tokens. Bearer tokens use `{{ownerToken}}`, `{{editorToken}}`, etc. The environment also contains `collabProblemId` and each account's `UserId`, `Username`, and `Email`. Generated token files are ignored and must not be committed. Scripts, README and request files can be committed.

Setup and login are separate phases: if login fails, committed fixture data remains; start the client server and run `login`. If the admin server is on another branch, switch/start it on the collaboration branch before running requests. No token is generated by bypassing the login API.

## API requests (no scenario order)

Requests are grouped by API. There is no shared scenario variable or numbered execution order.

| Request | Target after setup |
|---|---|
| Approved list | Owner, Editor or Reviewer authentication |
| Pending list | Owner authentication |
| Invite as Owner / Editor | outsider (not yet participating) |
| Editor to Reviewer | editor account (Approved) |
| Reviewer to Editor | reviewer account (Approved) |
| Approve / Reject | pending account (Pending) |
| Remove | reviewer account |

Run `node scripts/collaborator-test.cjs setup` from `apps/backend` to restore the fixture before independently trying a mutation. For example, Owner invite and Editor invite use the same outsider: reset before trying the other invitation. Approve and Reject use the same pending account: reset before trying the other action. Mutations change real local fixture state; these are individual API examples, not a collection intended to run all at once. No database reset is performed automatically by Bruno.

The approved list requests replace scenario-specific post-update and post-delete queries. Use them to inspect the current list whenever needed. Update requests use the existing editor/reviewer accounts and do not depend on invitation requests.

When running in WSL, the generated GraphQL URL uses its IPv4 address for Windows access. Run `login` after a WSL restart to refresh the address and tokens. Both client and admin servers must be running.

Fixture values and tokens are stored in ignored `collection/admin/collaborator.generated.js`, not a Bruno environment. The collection pre-request script loads this file for collaborator requests only; select Local. Other admin requests retain the existing login behavior. Regenerate with `login` when tokens expire.

## Representative permission errors

Five requests ending in FORBIDDEN verify denied access: Editor pending-list read, Reviewer invite, and Editor approve/update/remove. They assert the GraphQL error code, message, operation path, and absence of a successful result. HTTP 200 alone does not mean success for GraphQL. Run setup first if previous manual mutations changed the fixture roles (especially the reviewer account). These requests are expected to leave data unchanged.
